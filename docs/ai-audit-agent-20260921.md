## 结论

本轮以源码、自动化测试和本地构建为依据，不把配置页面、依赖声明、静态文案或测试桩当成已交付能力。

- 新增第 6 项已实现为**安全的分析摘要**：模型可选择返回一段公开、简短、按档位限长的依据摘要；应用只接收成对的 `<analysis_summary>` 标签，并在正式答案上方用默认收起的“分析摘要”展示。
- 不读取服务商的 `reasoning_content`，不把 `<think>` 当作公开内容，不伪造分析文字、运行时长或流式思考过程。服务商没有返回合法摘要时，界面不显示占位内容。
- “执行策略 / 档位校验 / 模型响应”等平台固定行已从成员可见进度中过滤；真实工作流、工具、审批与结果状态仍可见。
- OpenSquilla 与 Dify Marketplace **没有被导入或安装**。当前存在的是同频自己实现、经过测试的有界路由器和 Agent Harness；可以说明“设计受启发”或“功能等价的一部分”，不能对外声称已集成这两个项目。

## 新增第 6 项的安全边界

1. 只有普通文字回答会收到公开摘要指令；图片、视频、PPT、Computer Use 等严格 JSON 规划以及 Agent 续步 JSON 不会插入标签要求，避免破坏工具协议。
2. 摘要仅接受回答开头、完整成对的标签。缺失、嵌套、含控制字符或超过档位上限时直接丢弃摘要，不生成替代文案。
3. `<think>` 与 `<reasoning_content>` 内容会在进入工作区前清除；聊天兼容接口的 `reasoning_content` 字段和 Responses 的 reasoning item 也不会被解析为正文。
4. 当前服务商请求为非流式完整响应，因此“分析摘要”在回答完成后一次显示；没有伪造倒计时、逐字推理或假进度。
5. 快速、标准、深度、Pro 的摘要上限分别为 80、140、240、360 个字符。简单寒暄或没有可靠依据时允许完全省略。

## 新增第 34 项：服务端静默调度

- 普通对话走真实模型的 `dispatch` 决策，回复为文字/追问或 image、video、presentation、computer 意图；使用原 `/api/ai/chat` 的档位、配额预留、幂等及实际 Token 账本，不是前端正则或固定进度文案。
- 图片/PPT 在同一条对话内继续真实规划与执行；视频显示紧凑参数区由用户明确发送；电脑动作进入已有安全确认。调度决策本身不构成任意工具的执行授权。
- Node 定时器与 Cloudflare Cron/DO 可在页面关闭后推进持久化 Harness 的受限模型决策；新工具只进入等待授权，不自动付费或操作电脑。
- 旧记录迁移的 `background_capable` 默认 0，不在部署后接管历史遗留任务。每次运行重新核验账号状态和租户；停用候选退出后台队列，避免阻塞后续有效任务。事务抢占和存储幂等避免重复续步。
- dispatch 文字 JSON 中可带限长的公开 `analysisSummary`，非法摘要被丢弃而正式答案保留；不伪装为实时内部推理。
- 后台代码已包含于 `571bbd9`；主任务实际部署和安装结果以总验收报告为准。
