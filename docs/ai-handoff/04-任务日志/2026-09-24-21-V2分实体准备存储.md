2026-09-24（Asia/Hong_Kong）。基线 `032de57`。只新增 AI 工作台后端独立准备表和内部仓库，不新增 HTTP 路由、不修改 V1 客户端/保存协议、不迁移真实账号，也不触碰“我的任务”“客户脉络图”及 WorkBuddy 手机预览。

## 这一步解决什么、没有解决什么

#27 的根因仍是 V1 每次保存整账号工作台快照并受 8 MiB 限额约束；此前影子表只能把同一份 V1 数据拆段预览。本包建立独立 V2 `meta / entities / entity_chunks / mutations` 四表，并让 Node 与真实 Cloudflare Durable Object 初始化空表。只有测试或未来显式维护调用 `prepareFromShadow()` 才会从已校验的影子快照逐实体写入准备区；日常登录、GET、聊天、后台任务均不会自动准备或读取它。

准备期间，先在事务外算实体 SHA-256、以 48 KiB 原始字节分块（每 SQLite 行 Base64 ≤64 KiB）；同步事务内再核对 V1 revision、canonical 内容以及影子来源 revision/hash/time，失败整笔回滚。每行按租户与账号复合隔离，实体可单独按 ID 读取，读取时验证 V1 仍权威、源 hash、分块序列/大小/实体 hash。`activated_at` 永远留空；V1 的 `schema_version` 和对旧端的行为不变。

这只是可验证的**准备层**。没有逐实体客户端队列、独立 CAS/幂等写入、私有媒体引用、所有后台消费者的版本感知读取和旧端拒写前，不可启用 V2，更不能称“空间不足”已经修复。
