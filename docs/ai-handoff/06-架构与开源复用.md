# 架构与开源复用边界

## 决策职责

- 同频仍是唯一的账号/租户、授权、四档、额度账本、素材与任务权威入口；每个 run 仅有一个推进决策引擎。
- LibreChat 只在核验并真正接入的聊天消息/流式消费/内容渲染模块范围内复用，不宣称移植整个 LibreChat，也不新开绕过同频身份的聊天服务。
- Dify 用于获批准的指定工作流；沙盒内置工具运行并不代表同频工具已接通。远端 run 映射、未知结果冻结、账本和调用凭证必须由同频验证。
- OpenSquilla 若用于原第 8 项，需调用官方运行时/权重或获准的等价替代；当前自研 `server/ai/autoRouting.ts` 不是它。

## 当前事实与待落实选择

`ChatMessageRow.tsx` 的正式聊天正文由 `MarkdownReply.tsx` 渲染；`server/ai/providerStream.ts` 到 `server/ai/chatStream.ts` 的流已存在。已选定**最小完整功能模块移植**：LibreChat v0.8.7 精确提交 `9e74cc0e57b395926122bd4062c1fcedc48ed465` 的 GFM 消息分块与已完成块 memo 行为；源码分块抽到 `shared/librechatMarkdownBlocks.ts`，经 `librechatMarkdownBlocks.tsx` 薄适配接入真实 `ChatMessageRow → MarkdownReply`。同一分块器在服务端结算后生成 `AiChatResponse.richContent` 的 UTF-16 区间，**不复制**模型正文；既有 `answer_delta` / `run_finished` 附可选 v1 身份，原 `content`、事件类型和工作区格式不变。它接收现有增量合并后的当前正文，也渲染保存重开的同一 `content`；并非另建演示网站。直接依赖 `mdast-util-from-markdown@2.0.3`、`mdast-util-gfm@3.1.0`、`micromark-extension-gfm@3.0.0`，与已有 `react-markdown`/`remark-gfm` 语法一致。保留同频认证、SSE、回放、存储、素材与额度，不新增 MongoDB/Redis/宿主。迁移无需数据格式变化，回退可用旧渲染器读取原消息。

该模块未移植上游 math/directive 和 code/artifact Provider，因为同频现有渲染器未启用对应语法与索引；这部分必须在未来有实际能力/测试时另行补齐。LibreChat 完整 SSE hook 与身份体系也未接入，不能把部分内容渲染复用称为完整平台、完整富媒体流或进程重启恢复。

Dify 现况及两次 0.1.1 私有插件安装失败见 [集成记录](../dify-engine-integration.md)。`DifyEngineAdapter` 尚未被 Node/Worker 主聊天入口调用；本地 `DifyRemoteRunStore` 是 WIP 持久化实现，不等于远端断线可恢复。不得创建公网隧道或未批准的生产服务。
